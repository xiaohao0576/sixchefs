# POS 产品中英柬三语名称 Skill

## 目标

在 `pos_custom_ui` 模块中，为 POS 产品提供以下非存储计算字段，并确保它们可用于 POS 前端打印和后端下载的收银结账小票：

- `name_en`：英文名称
- `name_cn`：中文名称
- `name_km`：柬埔寨语名称

适用范围：

- 普通产品
- `type = 'combo'` 的套餐父产品
- combo 的子产品

## 必须遵守的实现原则

1. 必须通过 `pos_custom_ui` 扩展实现，不修改 Odoo 原生模块。
2. 三个字段必须是 `compute` 字段，且不设置 `store=True`。
3. 不可直接依赖 `field._get_stored_translations()` 的结果作为显示值。
4. 必须使用 Odoo 的语言上下文读取机制，以获得标准 fallback。
5. 前端和后端数据注入必须同时覆盖普通产品、combo 父行、combo 子行。
6. 后端只要求注入收银结账小票 `order_receipt_generate_data()` 的 QWeb 数据；不要为了此需求改厨房小票后端数据。

## 多语言 fallback 背景

Odoo 的 translated `name` 字段以 JSONB 保存，例如：

```json
{"en_US": "点心套餐26.8"}
```

即使 JSONB 没有 `zh_CN` 或 `km_KH` 键，以下读取仍会回退到 `en_US`：

```python
product.with_context(lang='zh_CN').name
product.with_context(lang='km_KH').name
```

概念上等价于：

```sql
COALESCE(name ->> 'zh_CN', name ->> 'en_US')
COALESCE(name ->> 'km_KH', name ->> 'en_US')
```

因此不能这样实现：

```python
translations = product._fields['name']._get_stored_translations(product) or {}
name_km = translations.get('km_KH') or ''
name_cn = translations.get('zh_CN') or ''
```

原因：该方法只返回数据库中显式保存的翻译键，不包含 Odoo 的 `en_US` fallback。翻译弹窗显示有文字，也不代表 JSONB 中已经保存对应语言键。

## 产品模板字段实现

文件：`pos_custom_ui/models/product_template.py`

```python
from odoo import api, fields, models


class ProductTemplate(models.Model):
    _inherit = 'product.template'

    name_en = fields.Char(string='English Name', compute='_compute_pos_custom_names')
    name_km = fields.Char(string='Khmer Name', compute='_compute_pos_custom_names')
    name_cn = fields.Char(string='Chinese Name', compute='_compute_pos_custom_names')

    @api.depends('name')
    def _compute_pos_custom_names(self):
        for product in self:
            product.name_en = product.with_context(lang='en_US').name or ''
            product.name_km = product.with_context(lang='km_KH').name or ''
            product.name_cn = product.with_context(lang='zh_CN').name or ''

    @api.model
    def _load_pos_data_fields(self, config):
        fields_to_load = super()._load_pos_data_fields(config)
        for field_name in ['name_en', 'name_km', 'name_cn']:
            if field_name not in fields_to_load:
                fields_to_load.append(field_name)
        return fields_to_load
```

说明：

- 这是非存储计算字段；读取、导出和 POS 加载时都会计算。
- `@api.depends('name')` 负责在产品名称变更后使字段缓存失效。
- POS 加载字段中必须包含三字段，否则前端产品模型没有它们。

## 前端 JS 打印数据

文件：`pos_custom_ui/static/src/app/utils/printer/generate_printer_data.js`

继承并 patch：

```javascript
import { patch } from "@web/core/utils/patch";
import { GeneratePrinterData } from "@point_of_sale/app/utils/printer/generate_printer_data";
```

### 收银小票数据

覆盖 `generateLineData()`，为每条打印行注入三字段。字段必须同时放入：

- `lineData.name_en/name_km/name_cn`
- `lineData.product_data.name_en/name_km/name_cn`

标准收银小票 QWeb 通常从 `product_data` 读取商品信息，但双层注入可与其它打印模板保持兼容。

### 厨房小票数据

覆盖 `generatePreparationChanges()`，为每条厨房变更记录注入三字段。字段必须同时放入：

- `change.name_en/name_km/name_cn`
- `change.product_data.name_en/name_km/name_cn`

重要：厨房打印与收银小票的数据结构不同。厨房行使用 `change.product_id` 查找：

```javascript
const product = this.models["product.product"].get(change.product_id);
```

不要仅凭订单行索引匹配产品；combo 行和子行会使索引逻辑脆弱。

推荐辅助函数：

```javascript
const PRODUCT_NAME_FIELDS = ["name_en", "name_km", "name_cn"];

function getProductLanguageNames(product) {
    const languageNames = {};
    for (const fieldName of PRODUCT_NAME_FIELDS) {
        languageNames[fieldName] = product?.[fieldName] || product?.raw?.[fieldName] || "";
    }
    return languageNames;
}

function addProductLanguageNames(target, product) {
    Object.assign(target, getProductLanguageNames(product));
}
```

### Combo 规则

必须用实际运行时 payload 验证：

- combo 父行和子行最终都需要拥有三字段。
- 若 JS 注入已执行但某个字段仍为空，先检查对应 `product.product` 在 POS 内存模型中的 `name_en/name_cn/name_km` 是否为空。
- 不要仅根据后台翻译弹窗是否显示文字判断字段是否已存储；要检查 JSONB 原始值或 POS runtime 数据。

## 后端 QWeb 收银结账小票数据

后端下载收据使用：

```python
pos.order.receipt.order_receipt_generate_data()
```

原生数据结构大致是：

```python
{
    'lines': [
        {
            'product_id': ..., 
            'product_data': {...},
        },
    ],
}
```

在 `pos_custom_ui` 新建 receipt 扩展，例如：

- `pos_custom_ui/receipt/__init__.py`
- `pos_custom_ui/receipt/pos_order_receipt.py`

并在 `pos_custom_ui/__init__.py` 中导入 `receipt`。

实现方式：继承 `pos.order.receipt`，在 `order_receipt_generate_data()` 中调用 `super()` 后，对 `data['lines']` 注入三个字段。

推荐实现：

```python
from odoo import models


class PosOrderReceipt(models.AbstractModel):
    _inherit = 'pos.order.receipt'

    def order_receipt_generate_data(self, basic_receipt=False):
        data = super().order_receipt_generate_data(basic_receipt)
        product_templates = self.lines.product_id.product_tmpl_id
        language_names_by_template_id = {
            product.id: {
                'name_en': product.name_en,
                'name_km': product.name_km,
                'name_cn': product.name_cn,
            }
            for product in product_templates
        }

        for line in data['lines']:
            product_template = self.env['product.product'].browse(line['product_id']).product_tmpl_id
            language_names = language_names_by_template_id[product_template.id]
            line.update(language_names)
            line['product_data'].update(language_names)

        return data
```

限制：

- 这里只处理结账/收银小票数据。
- 不要为该需求修改 `_generate_preparation_receipt_data()` 或后端厨房小票。

## 后端 QWeb 使用方式

后端结账小票模板可使用：

```xml
<t t-out="line['name_cn']"/>
<t t-out="line['name_km']"/>
```

或：

```xml
<t t-out="line['product_data']['name_cn']"/>
<t t-out="line['product_data']['name_km']"/>
```

建议优先使用 `line['product_data']`，以贴合原生收据模板的商品数据层级。

## 验收与排错清单

1. 选择一个只有 `en_US` 键的产品：

```sql
SELECT id, name FROM product_template WHERE id = <template_id>;
```

预期：即使 `zh_CN`、`km_KH` 键不存在，三个计算字段都不为空，并回退为 `en_US` 名称。

2. 选择一个有独立中文/柬埔寨语翻译的产品。

预期：三个计算字段分别返回对应语言值。

3. POS 前端检查产品运行时数据：

```javascript
{
    name_en: product.name_en,
    name_cn: product.name_cn,
    name_km: product.name_km,
}
```

4. 前端收银小票：普通产品、combo 父行、combo 子行的打印 payload 均包含三字段。

5. 前端厨房小票：普通产品、combo 父行、combo 子行的变更 payload 均包含三字段。

6. 后端下载的结账收据：`order_receipt_generate_data()['lines']` 中，每个行对象和每个 `product_data` 都包含三字段。

7. 不要用以下现象作为“翻译已经保存”的判断：后台翻译弹窗显示了源名称。必须检查 JSONB，或检查 `_get_stored_translations()` 返回的原始键。

8. 升级 `pos_custom_ui` 模块后，重新加载 POS 数据/刷新 POS 资产，再进行前端验证。
